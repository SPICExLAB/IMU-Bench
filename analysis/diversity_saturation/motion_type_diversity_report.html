01 · What a motion type is

A motion type is one of 1,000 k-means centroids fitted to the frozen recipe_100pct encoder's representation of every 10.24-second window in the pool. Nothing named them; nothing curated them. The definition is entirely operational.

INPUT10.24 s window6 channels × 512 samples @ 50 Hz, wrist acc + gyro, per-channel z-scored
EMBEDfrozen encoderViT-1D alt-attn, MAE checkpoint at step 292,000; pooled CLS → 384-d
REDUCEPCA → 64-dkeeps 96.9 % of embedding variance
PARTITIONMiniBatchKMeansK = 1000, seed 42 — each centroid is one "motion type"

So a motion type is a region of representation space: a recurring wrist-IMU waveform shape that the pretrained encoder maps to nearby points. The resulting partition is fairly balanced — cluster sizes run 363 / 3,060 / 17,489 (min / median / max), and all 1,000 are non-empty.

The name invites two misreadings worth killing up front.

  • It is not an activity label. No type means "brushing teeth". Two windows in the same type share a signal shape, which may or may not share a semantic cause.
  • It is not an intensity level. base.yaml z-scores every channel per window before the encoder sees it, so absolute amplitude and the gravity offset are divided out. A type cannot encode "vigorous vs. gentle" — only shape: temporal structure, spectral content, and cross-axis geometry.

02 · What the types physically encode

To check the types are physical rather than an artifact of embedding geometry, I pulled 12 raw windows back out of the cache for each of the 1,000 types (12,000 windows) and measured five shape statistics directly on the signal. If type identity explains a large share of the variance in a statistic, the partition is tracking that property.

Read as an axis, the span of type means says the partition separates slow, near-periodic, rotation-free windows (dom_freq ≈ 0.3 Hz, spec_ent ≈ 0.61) from fast, broadband, rotation-rich ones (dom_freq ≈ 4.8 Hz, spec_ent ≈ 0.91) — a roughly 15× span in tempo. That is the concrete content of "diversity" in the grid experiment.

Data quality find

Type #259 holds 363 windows (0.010 % of the pool) whose signal is exactly constant — z-scoring a flat channel yields all zeros. They come from eatingspeed. Harmless at this scale, but they are being counted as a distinct "motion type" and are worth filtering at the loader.

03 · What one actually looks like

Statistics describe a type; they do not show it. Every window in the pool can be fetched back out of the cache by index, so each macro-family can be represented by its medoid — family centroid → nearest type → the window nearest that type's centroid.

04 · Are they modes, or tiles?

Every diversity number in this report is defined relative to a k-means partition, so it matters whether that partition discovers structure or merely imposes it. Two measurements, each against a matched null — a Gaussian sample with the pool's own mean and covariance, so the same shape and effective rank but no modes at all. Whatever the null scores is the floor any k-means run would produce on structureless data.

A motion type is a tile of a continuum, not a discovered category

The real pool beats the structureless null by roughly 2× at every K, so there is density structure in the embedding — this is not noise. But the absolute values say there are no separated clusters: at K = 1000 the silhouette is 0.044, and three seeds agree on only 28 % of the partition beyond chance.

Two consequences. First, individual types are not stable objects — a different seed produces a substantially different partition, so any claim about one particular type is fragile. Aggregate claims (coverage, richness, rarefaction, the family structure) are safe, because they measure how much of the manifold is spanned, which is seed-robust.

Second, the grid's K axis reads better as "how finely the manifold is covered" than as "how many distinct motions are present". That reading strengthens rather than weakens the grid result: it explains why diversity saturates so early. The pool occupies a low-effective-rank continuum (effective rank 12.2 of 64 dimensions), and once you have covered it, more samples add nothing.

05 · What it is in activity terms

Two sources in the pool carry real activity labels: the realdata block (pamap2, recofit, samosa, shoaib, ut_watch, utd_mhad, wisdm — scripted HAR protocols, acc + gyro) and capture24 (free-living annotation, acc only). Between them they cover both halves of the type space, so the types can be read as activity mixtures rather than geometry.

How the labels were attached — and one thing that had to be abandoned

capture24's labels were joined to the pool by window content (hashing raw float32 bytes): a fresh rebuild reproduced 100.00 % of its 1,432,721 cached windows, so the join is a proven bijection.

realdata could not be joined at all. Three attempts failed: a positional join matched 5 of 200 index probes; content-hashing the rebuilt train split matched 4.16 %; content-hashing every session (97,699 windows, a superset of the cached block) matched the same 3,887 windows. The v3 cache's realdata block is not regenerable from the current code — not a reordering, not a re-split, the window content itself differs.

So realdata's types are obtained by assignment instead: each labelled window is re-embedded with the frozen encoder, projected with the PCA-64 map and assigned to its nearest of the 1000 centroids. The PCA basis was never persisted, so it was recovered by least squares from the cached (embedding, PCA-64) pairs — exact, because the projection is linear, and it agrees with the true PCA on 99.3 % of nearest-centroid assignments. The full chain was then checked end-to-end: re-embedding 4,000 pool windows recovers their stored type 96.5 % of the time.

  • run_jog occupies 3 types, and one of them (#891) holds 71.7 % of it. cycle needs 10 types for 90 % of its mass, stairs 16, walk 46. For the fast, periodic end of the space a motion type is very close to a gait or cadence signature — nearly interpretable as an activity on its own.
  • rest_inactive needs 251 types for 90 % of its mass, spread over 555 in total. "Not moving much" looks like many different things to the encoder, and this is where most of the pool's 1000 types live.
  • capture24 shows the same shape on the accelerometer-only side. sleep is compact (53 types for 90 %), bicycling compact (48), while sitting (180) and standing (154) are diffuse. Free-living walking needs 102 types against realdata's 46 — scripted protocols produce a much narrower walk than walking-in-daily-life does.
  • Types carry real activity signal but are not activity-pure. Median purity is 53.2 % for realdata against a 31.2 % chance baseline, and 68.4 % for capture24 (Willetts 10-class) against 37.4 %. Well above chance, far below a taxonomy.

06 · Diversity per dataset

Two different things get called diversity, and they must be separated:

  • Richness — how many of the 1,000 types a dataset touches at all.
  • Evenness — how spread its mass is across the types it touches.

Raw richness is almost pure dataset size: capture24 has 1.4 M windows and ocdetect 1.25 M, so of course they touch more types than openwatch's 1,842. To make them comparable every richness figure below is also rarefied — the expected number of types in a random draw of exactly m windows, computed analytically. Rarefied richness is the column that actually answers "which dataset is more diverse".

What the table says

  • ocdetect is the most diverse source on every measure — highest rarefied richness at all depths, highest effective types (438 Shannon / 383 Simpson), evenness 0.92, and its most common type holds only 0.5 % of its mass. It is not just the second-biggest dataset; it is genuinely broad.
  • realdata punches far above its size. At 93,510 windows — 7 % of ocdetect's — it reaches 695 types against ocdetect's 731, and at a matched 32,662 windows the two are effectively tied (641.8 vs. 643.5). Per window, realdata is the richest source in the pool.
  • capture24 is the volume/diversity inversion. It is the largest dataset and ranks fifth in richness. Its evenness of 0.97 is the highest in the pool, but that is evenness across a repertoire of only 277 types — it distributes uniformly over a narrow space.
  • sonic, motionx and humanml3d are narrow and concentrated. humanml3d puts 45.6 % of its mass into a single type and has an effective repertoire of 4.8 types; sonic reaches 167 types but an effective 15.2. These are synthetic or tightly-scripted sources and they behave like it.
  • Marginal contribution is near zero for almost everyone. Removing any source except capture24 and ocdetect costs the pool at most one type. The pool's type coverage is heavily redundant.

07 · The shape of each distribution

Richness counts the types a dataset reaches. It says nothing about how its windows are spread across them — and a source can reach 700 types while living in twenty. The rank-abundance curve settles it: sort a dataset's types by size, plot each one's share of that dataset's windows. A flat line means mass spread evenly; a cliff means a few types carry everything.

  • capture24 has the most even distribution in the pool (Gini 0.332) — but recall from §06 that this evenness is spread over only 277 types. Even and narrow.
  • ocdetect is the only source that is both broad and even: 731 types, Gini 0.530, and no single type above 0.5 % of its mass. It is the closest thing the pool has to a uniform sample of motion space.
  • realdata and nymeria are broad but front-loaded — 695 and 643 types, but half their windows sit in 70 and 55 types respectively. Their tails are long and thin.
  • The synthetic sources are degenerate as distributions. sonic reaches 167 types but 84.8 % of it is in ten of them; humanml3d puts 97.1 % in ten and 45.6 % in one. For SSL purposes their nominal type count is close to meaningless.

08 · Where in motion space each dataset sits

A thousand bins is too many to read. Ward-clustering the 1,000 centroids into ten macro-families gives a legible distribution, and because each family has a measured physical signature, the axis means something.

The first thing the clustering does is worth stating on its own: the coarsest split in the entire type space is not motion, it is the sensor. Cut the Ward tree at two clusters and one side holds 248 types, 247 of which have identically-zero gyroscope — the accelerometer-only capture24 island, 38.2 % of all pool windows. Motion structure only appears below that split.

  • capture24 lives entirely outside the gyro families — 94.7 % of it in A1–A3, the rest in the mixed boundary family G1. It contributes no windows at all to the seven motion families where every other dataset lives.
  • ocdetect owns a private region. G4 is 159 types and 16.6 % of the whole pool, and it is 99 % ocdetect. Nearly half of ocdetect's own mass (46.7 %) sits there. This is why it leads every richness measure — and it is a caution, because much of its apparent diversity is a region no other dataset can corroborate.
  • The three synthetic sources collapse into one family. motionx 86.5 %, humanml3d 97.5 % and sonic 97.2 % of their windows all land in G7, the fastest gyro family, which holds just 5.4 % of the pool.
  • realdata, nymeria and eatingspeed spread across G2/G3/G5/G6 with different weightings — nymeria leans slow (G3 30.5 %), eatingspeed leans fast (G6 43.4 %), realdata sits between them (G5 32.1 %, G6 28.9 %). This is the real-motion core, and its three members genuinely differ in tempo distribution.
The synthetic sources re-weight; they do not extend

Inside G7, sonic and ocdetect share 34 of the family's 76 types, and 70 % of all synthetic-source mass sits in types ocdetect also occupies. So the near-1.0 JS distances in §09 come from proportions, not disjoint support: sonic puts 97 % of itself where ocdetect puts 11 %. Adding motionx, humanml3d or sonic to a pretraining pool mostly reweights a region real data already covers rather than opening a new one.

09 · Which datasets overlap

Richness says how much space a dataset covers; it does not say whether that space is already covered by something else. The matrix below is the Jensen–Shannon distance between each pair's distribution over the 1,000 types — 0.00 means the two datasets have identical motion-type mixes, 1.00 means they share no type at all.

  • capture24 is disjoint from everything (1.00 across the whole row). This is a sensor artifact, not a motion finding: capture24 is a wrist accelerometer with no gyroscope, so its gyro channels are zero-filled and the encoder can separate it on that alone. It owns 225 sole-occupant types purely because nothing else has a dead gyro. Treat capture24's apparent "unique diversity" as an instrumentation confound.
  • realdata ↔ nymeria at 0.47 is the only strongly-overlapping pair, with eatingspeed close behind (0.58 to both). These three form the real-wrist-motion cluster and are substantially redundant with each other.
  • humanml3d ↔ sonic at 0.83 is the tightest pair among the narrow sources — the synthetic sources resemble each other more than they resemble any real capture.
  • Across the pool, 248 types have exactly one occupant source and 287 have four — but occupancy is not the same as mass. The median type gets 98.1 % of its windows from a single dataset, and 653 of 1,000 types are over 90 % one source.
Correction — the K axis is more confounded with dataset identity than AMI suggests

An earlier reading of this quoted AMI = 0.26 as evidence that motion type is largely independent of source. That was the wrong statistic. Symmetric mutual-information scores are normalised by both entropies, and with 1,000 types against 11 sources the maximum attainable NMI here is only 0.328 — so 0.26 is 80 % of the ceiling, not 26 % of anything.

The metric that answers the question is the uncertainty coefficient U(source | type) = I / H(source): 0.80. Knowing a window's motion type removes 80 % of the uncertainty about which dataset produced it. Excluding capture24 it is 0.59; across just the four large real sources, 0.56.

So increasing K in the grid partly means "spanning more datasets", not purely "spanning more motion variety". The diversity effect measured there is real, but it is not cleanly separable from source diversity.

10 · The 5-source pool the grid actually used

The motion-types × volume grid was run on the five SSL sources only, with k-means refitted on that subpool (1,959,288 windows, cached at labels5src_k1000.npy). Type IDs there are not comparable to the 11-source IDs above, so the per-dataset diversity has to be recomputed in that space. Excluding capture24 removes the gyro confound, and the numbers change accordingly.

The ranking is unchanged — ocdetect > realdata ≈ eatingspeed ≫ sonic ≈ motionx — but the top three are now much closer together (961 / 905 / 867 types), and at a matched 30,000 windows ocdetect and realdata are separated by 4 %. Since the grid's "K largest clusters" are picked largest-first, and 607 of 1,000 types are shared by three or more sources, the low-K cells of the grid are effectively drawing from the common core that ocdetect, realdata and eatingspeed all occupy — not from any single dataset.

That is consistent with what the grid found: diversity buys 14.9 % MAE loss at fixed volume, most of it between K = 1 and K = 5, and volume stops paying above roughly 2,000 windows. The types are shared, so a few thousand windows spanning many types already contains most of the pool's structure.

11 · Caveats

  • Circularity. Types are defined in the recipe_100pct encoder's own embedding space, and that encoder was pretrained on this pool. A dataset scores as "diverse" partly because the encoder learned to spread it out. Fine for comparing sources within one fixed space; not a claim about intrinsic motion diversity.
  • capture24's separation is instrumentation, not motion. Accelerometer-only, gyro zero-filled — see §09. Any conclusion resting on capture24's 225 sole types is measuring a missing sensor.
  • K = 1000 is a choice. Richness is defined relative to it; a different K would rescale every number, though the ranking is unlikely to move.
  • Tiny sources are estimates. imuposer (137 windows) and totalcapture (461) cannot support anything beyond the @137 rarefaction column. Their Shannon values are downward-biased by small-sample effects.
  • ocdetect's lead is partly a private region. Family G4 — 159 types, 16.6 % of the pool — is 99 % ocdetect, and holds 46.7 % of ocdetect's own mass. Its top ranking on every richness measure rests in part on territory no other dataset enters, so it cannot be independently corroborated.
  • The realdata cache block is not reproducible. Only 4.16 % of mae_multidata_cache_v3/realdata_train_x.npy can be regenerated from the current code and config, even scanning every session. capture24 reproduces at 100 %, so this is realdata-specific — but any analysis that assumes a fresh realdata build matches that cache is unsafe, and this one had to route around it (§05).
  • realdata's activity names come from assignment, not identity. Labelled windows are re-embedded and assigned to the nearest centroid, which reproduces the pool's own stored types 96.5 % of the time — so roughly 3–4 % of those assignments are wrong. Fine for the aggregate shape reported here; not for claims about a single type.
  • Purity is single-source. A type's activity purity is computed over the labelled windows of one dataset, which for most types is a minority of their membership. It describes what that source contributes to a type, not the type as a whole.
  • Single k-means fit, seed 42. No re-fit variance was measured. MiniBatchKMeans at K = 1000 is not guaranteed to land in the same partition across seeds — §04 measures exactly how far it is from doing so (ARI 0.280).
  • Partition-free cross-check. The effective rank of each source's PCA-64 block broadly agrees with the cluster-based ranking, with one exception: openwatch's effective rank is 3.76 against a pool value of 12.18, i.e. it is far more collapsed than its 98 types suggest. capture24 also sits low at 6.66.
